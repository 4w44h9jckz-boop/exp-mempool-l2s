# Simulation base

`emem_sim` runs the reference pools of `ref/python` on a simulated network.
Every run is a function of its `Scenario` and seed.

| Module | What it does |
| --- | --- |
| `events.py` | The discrete-event scheduler: time, then scheduling order |
| `batch.py` | What a node pays to verify proofs under one key, alone or as a batch, from Commonware's single-threaded measurement, and the bisection of a batch that fails (decision record 0025) |
| `network.py` | Nodes with their own `TxPool`, a random topology with per-link latency, and go-ethereum's gossip: push to a fixed $\lceil\sqrt{n}\rceil$ of $n$ peers per sender, announce to the rest, fetch after 500 ms, and fetch a refused transaction again unless it was underpriced or is on chain (decision record 0004); hooks on every admission answer and every block import. Under a profile with dependency frames (EIP-8288), a transaction with dependencies travels only in wrappers: a user's to the node it chose, every node's aggregate to every peer each `aggregation_interval` after an optional `prove_delay` and its proving time (AG-9), a node proving one aggregate at a time and skipping the ticks that come while it proves, and with `forward_wrappers` every user's wrapper relayed once to every other peer (decision records 0013 and 0034). Sealed transactions (EIP-8184) gossip as transactions of their size, and a committed one counts as on chain. With `announce_budget`, announcements carry each frame transaction's rule 6 budget and a node does not fetch one above its own `max_verify_gas`, forgetting or, with `remember_budget`, remembering the hint; `liars` relay nothing and, with hints, announce every hash as over any bound (decision record 0016). With `record_heard` every node records when, and from which peer, it first heard of each hash, and `spies` take no part in the random topology, are then connected to every node, and relay nothing (decision record 0021). With `batch_window`, a node verifies the proof a transaction carries under one shared key before its pool sees it, on one core whose time delays the admission: each on arrival, or held for a window, or until `batch_max`, and verified as one batch, bisected when it fails (decision record 0025) |
| `chain.py` | One block per slot, built by a proposer, in turn through every node or through a tuple of them or with `draw` drawn from the tuple each slot, from its own pool with `emem.build_block`, delivered to the others after a delay; finality on the beacon chain's happy path, so a block is final 64 to 95 slots after it was produced and every node hands newly final blocks' frame gas to its pool's `finalize` (MD-8) when it imports the block that finalizes them; under a sealed profile each block commits sealed transactions from its proposer's pool and executes the previous block's commitments first (LU-12, LU-13); under an inclusion-list profile a committee drawn each slot from a stream of its own builds its lists at `il_at` (IL-2), the next block must satisfy them or the slot has no block (IL-8), leaving a gap in the heads' slots (RR-2), and builders and includers in `filtering` and `filtering_includers` leave out what `censored` names, a filtering builder stuffing, missing, yielding the slot to the next builder that does not filter, or doing the cheaper of stuffing and yielding, and recording what filtering cost it against the block it would have built honestly (decision record 0018); and each function in `key_publishers` names, once a block is built, the commitments whose keys are withheld, which the next block then carries as not `revealed` (decision record 0032); and with `dimensions` `two` every block counts execution and state gas apart under BB-6 and records both sums (decision record 0043); a transaction whose execution reverts is in its block, at the gas it used, and the block records it under `reverted`, and with `drop_reverting` every builder leaves such a transaction out instead (BB-5, BB-7, decision record 0045) |
| `workload.py` | Poisson demand, each load from random streams of its own: `TransferLoad` for plain transfers, `FrameLoad` for self-paying or sponsored frame transactions, `SharedSenderLoad` for spends from a shared sender, sent by a relayer or by their users (decision record 0005), optionally with an expiry frame, 256-bit nonce keys, a relayer that sends every spend at once and sends again what its node refused or dropped, users that send only to some nodes, and users that meet MATCHA's load floor (MA-13) at the node they send to; `JunkLoad` for an adversary at one node that sends spends meant never to land, and optionally invalidates them every block; `FanOutLoad` for an adversary that rests many transactions on one payer and moves its balance every block, `SponsoredLoad` for a paymaster service's users and `WalletLoad` for wallets that pay for themselves, which resend after every block and give up at a deadline, and `FloodLoad` for an adversary that keeps every frame pool full of transactions no builder includes, or that pay only for the block they fill, or whose default-code sponsor drains itself in the next block, optionally each with an EIP-8288 dependency of its own and sent as a wrapper (decision record 0034), all built by `backed_tx` in one of five payment shapes, optionally with an expiry frame or an EIP-8288 dependency frame; `SponsoredLoad` and `WalletLoad` send a transaction with a dependency as a wrapper with its proof, may send each once, may send only to some nodes, may carry another signature entry, such as a proof in an ARBITRARY one, and may take a sender of its own for each arrival (`fresh`); `SealedLoad` for senders of EIP-8184 sealed transactions with a ToB fee and a tolerance for preceding commitments of their own, which send again after every block that does not commit them, optionally re-encrypted; `SealedFlood` for an adversary that keeps every sealed pool full of sealed transactions that tolerate no commitment before them, at one ToB fee or each above the last (decision record 0015); and `SybilLoad` for an adversary that backs sponsored transactions with default-code sponsors of its own, each holding nothing and handed to one node or several, or one a round that holds enough and whose transfer of its balance lands before them (decision record 0019); and `CopiesLoad` for spends from a shared sender that each user hands out at once as copies to different nodes, with the nullifier in the nonce key or in a slot of the sender's storage (decision record 0020); `RootWriter` for a root source that writes a root every slot (EIP-8272), and `RootSpendLoad` for spends from senders of their own that prove against its latest root, send again after every block, and prove again when a node refuses the root (decision record 0023); `BumpLoad` for plain transfers whose wallets re-price the oldest pending transaction, or every one, that their node has imported a number of blocks without, by NP-11's least bump or to the market, from users who stop at a price of their own, and `patience` on `SharedSenderLoad` for spend users who sign a re-priced version that the relayer sends in place of the old (decision record 0024); `ProofLoad` for frame transactions that carry a proof under one shared key, and `InvalidProofLoad` for proofs that fail, each handed to every node (decision record 0025); `reads` on `SharedSenderLoad` for spends whose prefix reads nothing of the pool's storage, a slot of their own, or a root that `SlotWriter`, a depositor, rewrites every block, and `JunkLoad` reading a setting for each junk spend or one in each of many applications, with a flip of every setting its node holds junk for (decision record 0026); and `publishers` on `SealedLoad` for payments that name one of several key publishers, of which some withhold every key, and whose senders send a withheld payment again at the next nonce, sealed or as a regular transaction, and `revealed` on `SealedFlood` for a flood that withholds every key (decision record 0027); and `Committee` for an MPC committee that queues the intents each block its node imports carries, cuts batches every block or when full, and settles each after its rounds as one padded transaction proved against where the last ends, from an account, from one frame transaction at a time or from a nonce key for each batch, optionally re-pricing one its node has imported a block without (decision record 0028); and `Clearing` for a committee of member nodes that clears a batch every block, of the orders a block carried once every member has imported it or of the orders every member holds at a cutoff the rounds and a margin before the block, each batch after the last for a number of rounds at a round trip, settled from an account (decision record 0029); and `expiring` on `SharedSenderLoad` for spends in EIP-8266's expiring-nonce mode under the reserved key, with an expiry frame a number of seconds after the head's timestamp, the mode's gas in the paying frame and the nullifier in a slot of the sender's storage, signed again by their users when a version can no longer make the next block (decision record 0030); and `HotWallet` for plain transfers from accounts that send many, at once, serially or in batches, before and after their delegation, and `Upgrade` for a sponsor's type 4 transactions that delegate them, each authorization signed at its account's next nonce by a wallet that keeps sending, pauses, or drains first (decision record 0031); and `KeyCommittee` for a threshold committee as a key publisher, whose $n$ members' shares are counted in time or not each slot or each commitment, with members that always withhold, senders that release their own keys, and a new committee every epoch that reshares the key or rotates it, named by `committee` on `SealedLoad` for a share of its payments, whose senders learn of a withheld key at the committee's deadline and keep or reseal at a rotation (decision record 0032); `Updater` for an open-role updater that proves a pool's root from its chained outputs, racing or backing off (decision record 0039); and `Tickets` for blind tickets bought under keys at a Poisson rate as plain transactions, each spent from a shared sender a holding time after its node imports the block that carried it, through that node or a random one (decision record 0040); `state` on `TransferLoad` and `state_gas` on `SharedSenderLoad` for EIP-8037 state gas, drawn or fixed, in a type 2 transfer's limit or in a spend's verifying frame for a nonce key and its sender frame for a storage slot (decision record 0043); and `ShuffleRounds` for shuffle rounds from one publisher, one after another, each attempt coordinated off chain and sent as one transaction that pulls every input's unit and pays every output, in the public pool or sealed, or as a lock that skips an input that cannot pay and a settlement after it, with a publisher that leaves out an input it sees cannot pay and a griefer that holds one seat a round and spends its unit as the round is sent (decision record 0046) |
| `metrics.py` | The recorder (submission, first pending time per node and the route it came by, admission results, removals, inclusion, each block's proposer, what each block's builder skipped and why, each block's sealed commitments and how many decrypted transactions it ran, wrappers sent and received with their proofs and bytes, when a transaction was first listed and by how many lists, missed slots, periodic samples) and table helpers |
| `parallel.py` | `run_all`, which runs independent simulations in as many processes as there are processors, or `EMEM_JOBS`, and returns their results in order (decision record 0018) |
| `scenario.py` | `Scenario` (everything a run depends on, including the sealed pool's profile and, through `frame_pools`, a frame pool profile per node chosen once the topology is drawn; an address given code and no balance starts with none) and `Simulation` (the wiring, including each node's aggregation ticks at a phase drawn from a stream of their own, and the inclusion-list committee's stream) |

```python
from emem import Head
from emem_sim import Scenario, Simulation, TransferLoad, percentile

senders = [f"u{i}" for i in range(100)]
sim = Simulation(Scenario(seed=1, nodes=20, accounts={s: 10**20 for s in senders},
                          genesis=Head(timestamp=0, gas_limit=2_100_000, gas_used=1_050_000, base_fee=10**9)))
sim.add_load(TransferLoad("t", rate=3.0, senders=senders))
rec = sim.run(600)
print(percentile(rec.inclusion_delays(), 50))
```

Both `ref/python` and `sim` must be on the import path
(`PYTHONPATH=ref/python:sim`); experiment scripts set it themselves.

What the simulation leaves out is listed in each module's docstring. The most
important omissions are bandwidth, private order flow, and wallets that react
to prices.

```bash
PYTHONPATH=ref/python:sim python3 -m unittest discover -s sim/tests
```

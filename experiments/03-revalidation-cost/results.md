## 1. How many transactions one payer can make every node re-simulate

An adversary sends 1024 transactions resting on one payer it controls to every node 30 s into the run, at a fee cap and tip of 1 wei, so that no builder includes them; from 60 s, after every block its node imports, an account it controls sends the payer 1 wei in a 21,000-gas transfer, which lands in the next block, five times. Held is the adversary's transactions per node when the touches begin; capital is the summed `max_cost` they reserve at one node, in wei, and what it would be at a fee cap of the genesis base fee, 1 gwei. Re-simulations and code gas are per node per block that carried a touch: code gas is the declared limits of the prefix frames whose target holds code the protocol does not define, here 80000 for each sender with code and 10000 for a non-canonical paymaster. Re-simulations in other blocks are per node per block after 60 s. The ratio is code gas per node against the touch's 21,000 gas.

## 3. An honest paymaster's users

Users of one paymaster service, each a sender with code (30,000 gas of verification), send 1500 transactions an hour for an hour, and 7500 more an hour from minute 10 to minute 20: about half the base fee's target, then half again the block's capacity (the first table). Each user has one transaction in flight and sends it again to a random node after every block that does not include it; nobody raises a fee. The payer is a canonical paymaster, or under `hegota-testnet` a default-code sponsor, which that profile caps at one pending transaction. Landed is an hour's inclusions, delays are seconds from first submission. Re-simulations and code gas are per node per block, over the run and, for re-simulations, over its second half; held is the payer's pending transactions per node at a block. Busy is `ErrFramePaymasterBusy` answers per transaction asked.
